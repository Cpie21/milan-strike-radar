# 一句话问罢工：AI 查询设计（2026-10-04 原型）

## 定位

不是聊天机器人。用户用一句自然语言进入系统，系统把它拆成一组结构化判断，最后用**可核对的界面**作答，而不是用一段 AI 生成的文字作答。

> AI 负责理解和筛选，数据库提供事实，UI 负责建立信任。

## 链路

```text
自然语言问题
  │
  ├─ ① 理解 ── 规则：日期 / 时刻 / 城市 / 线路 / 交通关键词      （lib/ask/parseQuery.ts）
  │            Jev：意图（5 选 1）+ 4 个交通方式是非题，一次请求并行
  │
  ├─ 分支 ──── 无关问题 → 拒答并给示例
  │            缺日期（行程 / 单日类问题）→ 追问：今天 / 明天 / 本周 / 两周 / 选日期
  │            缺交通方式（行程类）→ 追问：火车 / 地铁 / 公交 / 机场
  │            单日、没说交通方式 → 不生成卡片，直接跳到当天页面
  │            一段时间 → 按天列出（不需要逐条判断）
  │
  ├─ ② 检索 ── 数据库按日期范围 + 城市（本页城市 + 问题里提到的城市）+ 交通方式取候选
  │            坐飞机的行程，同时取火车和公交（去机场的路）
  │
  ├─ ③ 判断 ── 每条候选一次 Jev 请求，全部并行（上限 8 条）：
  │            是否相关（是非）· 关联方式（5 选 1）· 建议动作（6 选 1）
  │            · 官方信息是否充分（是非）· [核实消息时] 消息是否属实（3 选 1）
  │
  └─ ④ 证据 ── 相关度阈值 0.35 · 影响等级排序 · 数据同步时间 · 官方来源链接
```

接口是流式返回的（NDJSON）：每完成一步就推送一步，前端把"正在做什么"实时显示出来。

## 谁来判断什么

| 判断 | 谁做 | 原因 |
|---|---|---|
| 日期、"周五""下周三"、时刻、城市、线路号 | 规则 | 能精确读出来；Jev 不擅长处理日期 |
| 你的时刻是否落在罢工 / 保障时段内 | 代码 | 纯时间运算 |
| 影响等级（高 / 中 / 低 / 无 / 已取消 / 待公布） | 代码 | 由状态、时段和时刻重叠关系唯一决定 |
| 问题意图 | Jev | 语义判断，答案可以枚举 |
| 这条罢工和你的行程有没有关系 | Jev | 例如"Trenord 地方罢工"和"坐 Frecciarossa 高铁"无关，这需要语义理解 |
| 建议动作 | Jev 提议，代码把关 | 已取消、时段待公布、在保障时段内、不在罢工时段内，这几种情况由规则直接决定，覆盖模型的建议 |
| 消息属实 / 夸大 / 不符 | Jev | 比对用户听到的说法和官方记录 |
| 罢工事实本身 | 数据库 | 唯一的事实来源 |

## 界面如何建立信任

- **先给结论**（颜色对应影响等级），下面是每条罢工的卡片：24 小时时间条（红色是罢工、绿色是保障，再标出"你的时刻"）、时段、受影响线路、建议动作、官方来源链接、"查看当天全部"。
- **每个事实都标出来源**：`规则` / `Jev xx%` / `数据库` / `默认`。百分比是 Jev 校准过的把握程度。
- **被排除的记录也展示**："已排除 N 条与你无关的记录"，附上排除原因和把握程度。
- **判断过程可以展开**：4 个步骤、每一步识别出了什么、用时多少、花了多少钱。
- **底部注明**数据同步时间（罗马时间），并说明"规则"和"Jev"分别是什么意思。
- **Jev 不可用时**自动降级为规则匹配，并明确告诉用户。

## 成本与防护

- 一个行程类问题：1 次理解请求 + N 次判断请求，实测约 $0.0001，耗时约 1 秒。
- 问题最长 200 字；每个 IP 每分钟最多 8 次（单实例、内存实现，上线前需要换成共享存储）；Key 只在服务端使用。

## 已知局限（原型阶段）

- 没有区分航空公司。比如易捷机组罢工只影响易捷的航班，但现在没有追问"你坐哪家航空公司"。
- "这周 / 最近"这类时间段问题只按天列出，不做逐条判断。
- Jev 的概率在这个场景下是否真的校准过，还没有用人工标注的测试集验证。
